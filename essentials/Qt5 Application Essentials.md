## What is *meta-object compiler(MOC)*?

A code generator that scans your C++ headers for  Q_OBJECT  and related macros and produces extra C++ code to implement Qt’s meta‑object features like signals/slots, runtime type info, and dynamic properties. CMake use [property `AUTOMOC` to specifying whether moc will be invoked](https://cmake.org/cmake/help/latest/prop_tgt/AUTOMOC.html?utm_source=perplexity) (it should always be YES).

## Qt widgets application Vs Qt qml application

Qt Widgets uses standard C++ code to create traditional desktop layouts, while QML is a declarative, JavaScript-like language designed for fluid, modern, and animated UIs, [more details here](https://share.google/aimode/BHL4jfJ2ADVukj4Mf).

## How to create a custom widget?

`New File` → `Qt` → `Qt Widgets Designer Form Class`, this will create 3 files: .ui, .h, and .cpp files for the widget, the widget has a member `ui` points to a **ui_xxx.h** file generated by **User Interface Compiler (UIC)**. To make the custom widget useful, you should do tasks like:

* Design the ui by dragging in widgets.
* Initialize widget, e.g. connect `signals` with `slots`, setup children widgets, etc.
* Implement slots

## What is `signal` and `slot`?

`signal` is a message sent by an object, a connected `slot` is the function to be invoked when a `signal` is triggered.

`signal`s are declared as:

```c++
class MyObject: QObject {
  Q_OBJECT
signals:
  void signal1(int arg);
};
```

and emit like `emit signal1(42)`, don't implement `signal`, **moc** will generate it for you.

`slot`s should be declared as:

```c++
class MyObject: QObject {
public slots:
  void handleSignal(int arg);
};
```

Or just use **lambda**s.

Besides, **signal** could connect to another **signal**.

## What are buddy widgets?

A buddy widget accepts input focus on behalf of a `QLabel` when the user type the label's shortcut key combination. A `QLabel's shortcut key combination is set by its name, you prefix *&* before the mnemonic, e.g. "ho&me", then **alt+m** is its shortcut.

## What is `QObject`'s **thread affinity**?

Each `QObject` has a thread to handle its event loop, that is called **thread affinity**. It setup thread affinity to the thread that create it until it is moved into another thread.

The confusing part is `QThread` is an `QObject` as well. So it has thread affinity to the thread that creates it but not the worker thread where its `run` method is executed in.

The following is a common pattern to use QThread:

```cpp
class Worker : public QObject 
{ 
    Q_OBJECT 
public slots: 
    void doWork()  
    { 
        emit resultReady("workers are the best"); 
    } 
 
signals: 
    void result(QString data); 
}; 
 
// Somewhere in MainWindow 
QThread* thread = new QThread(this); 
Worker* worker = new Worker(); 
worker->moveToThread(thread); 
 
// Signal QThread::finished is emitted in the associated thread
// and it's handled in worker thread, use a DIRECT connection
connect(thread, &QThread::finished,  
        worker, &QObject::deleteLater); 
// Signal is emitted in current thread, use a QUEUED connection
connect(this, &MainWindow::startWork,  
        worker, &Worker::doWork); 
// Signal is emitted in work thread, use a QUEUED connection
connect(worker, &Worker::resultReady,  
        this, &MainWindow::handleResult); 
 
thread->start();
```
